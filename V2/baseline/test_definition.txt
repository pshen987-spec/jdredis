v2 baseline workload definition
===============================

Version isolation
v1 is a snapshot of earlier scripts and documents. v2 is the new workload definition; v1 and v2 performance numbers must not be used as direct A/B optimization evidence. This revision changes workload SET Values from normally distributed sizes to fixed 200KiB; prewarm Values remain normally distributed. Results from before this revision are a different workload and must be labeled separately. Future optimization v2 variants must use the same seed, key universe, load level, command mix, warmup distribution, fixed workload SET size, TTL, and Redis resources as this baseline.

Key and Value
- Default universe: 400000 keys, test:v2:data:0 through test:v2:data:399999.
- Each round first writes every Key in this universe with SET EX 1, using a batch of 1000 pipelined commands and a truncated normal Value-size distribution. The prewarm is outside stage2/3 metrics. Its writes and expirations are part of the allocator history even though most early Keys will no longer be live when stage2 begins.
- SET and GET pick independently and uniformly across the entire universe. No fixed hot key and no separate keepalive thread.
- Prewarm Value size: draw from N(200KiB, (190/3)KiB), round to integer KiB, redraw outside 10..390KiB. Normal workload SET and APPEND each send a fixed 200KiB payload per command. Pseudorandom bytes are pre-generated by size to avoid making random-number generation the client bottleneck; the byte content is deterministic for a given size and seed.
- SET uses EX 1. APPEND is a native single Redis command: it leaves an existing Key's TTL unchanged, and creates a Key without TTL if the Key is missing. APPEND RTT contains only APPEND. Each workload round starts after a Redis flush, so persistent APPEND-created Keys do not carry over to the next round.
- If achieved SET throughput is 8000/s, only roughly 8000 of 400000 keys may be live. A GET hit rate near 2% is therefore plausible. Always show GET hits, misses and response bytes; 13000 GET OPS does not imply 13000 large Values/s.

Load and phases
- Multiplier 1.0 runs 20 SET and 20 MGET threads in stage2. Stage3 adds 40 GET and 5 APPEND threads. SET workers pause 2ms after each successful command; APPEND workers choose one random key, append five times, then pause 100ms.
- The current sweep defaults to thread multipliers 0.5, 0.75, 1.0, and 1.25; older runs also covered 1.5 through 3.0. Thread counts are rounded per group. A thread multiplier does not guarantee the same multiplier for achieved OPS. 8000 write OPS + 13000 read OPS is a reference point to locate in the measured capacity curve.
- Stage2 runs 30s to establish steady state, stage3 runs 60s as the main measurement window.
- An MGET logical operation reads 100 distinct random keys and counts as one read OPS. Redis physical OPS also includes phase markers; distinguish client business OPS from server INFO OPS.
- ABNORMAL_SET_SHARE=0 by default. A positive value injects 512KiB SET Values. Unmodified baseline Redis is expected to accept these; later Redis Server protection is expected to reject SET Value >=500KiB and APPEND resulting Value >=500KiB.

Measurements
- Per command and stage: attempted, successful, failed, average and maximum RTT, successful RTT>5ms, GET/MGET hit and miss, returned bytes, abnormal Value count.
- 185: Redis CPU, RX/TX, used_memory/fragmentation, replication offset/link, network drops and errors. The client also prints its own process average CPU cores by phase to detect a client-side bottleneck.
- 5ms is a business RTT threshold, not a socket deadline. The client socket read timeout remains 100ms.
- Capacity is determined from achieved successful OPS as concurrency rises, alongside RTT>5ms, errors, network traffic, and Redis CPU. A plateau or degradation must be checked against client CPU/resource exhaustion before assigning the bottleneck to Redis. Error/RTT limits for declaring "sustainable" need to be stated with the report.
