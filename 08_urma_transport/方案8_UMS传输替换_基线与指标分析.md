## 0. 结论

方案8 用 **UMS（UB Memory based Socket）** 把 Redis 与压测客户端之间的 TCP 数据面替换成 UB，应用代码 0 行改动。

- **传输替换生效**：客户端 3,209 个 `/proc/net/ums` 采样 **0 条 Fallback=True**；25G 网卡阶段3 TX 峰值从 2,468,994kB/s 降到 **209kB/s（-99.99%）**，数据全部走 UB；
- **容量提升**：阶段3 成功命令 711,440 → **877,067（11,857 → 14,618/s，+23.3%）**；阶段2 294,651 → 414,402（+40.6%）；
- **5ms 比例大幅改善**：阶段3 `>5ms` 571,046（80.27%）→ **368,021（41.96%），-38.31pp**；阶段2 5.69% → 1.01%；
- **平均 RTT 下降**：阶段3 MGET -8.7%、SET -16.0%、GET -25.5%、APPEND -22.4%；阶段2 MGET -37.5%、SET -25.0%；
- **但主线程仍 97%**：`usr 22.24→26.13`，`sys 74.50→70.88`，只降 3.62pp；每命令 core-us 从 81.6 降到 66.4（-18.7%），同负载估算主线程约 **80%**，不是 60%；
- **Value 拷贝没有消除**：`cmdstat_get` 6.7 → **6.78us（+1.2%，不变）**；`cmdstat_mget` 31.8 → 26.81us（-15.7%）；`cmdstat_append` 64.3 → 59.51us（-7.4%）；
- **5ms 仍未达标**：阶段3 仍有 41.96% 命令 >5ms；且出现新的尾部问题：GET max **21.3→62.9ms（+195%）**、APPEND max **20.7→64.0ms（+210%）**，四类命令 max 全部聚在 **62.9~66.4ms**。

一句话：**UMS 用 UB 替换了 TCP 数据面，拿到 +23% 容量和 -38pp 的 5ms 比例；但没有消除用户/内核拷贝、RESP 和 Value memcpy，主线程仍是瓶颈，5ms 目标要靠下一步的 URMA 零拷贝。**

## 1. 方案实现简述

### 1.1 为什么使用 UMS

冻结基线阶段3 的主线程 CPU 为 **97.00%**，其中：

| 指标 | 基线值 |
|---|---:|
| 主线程稳态 CPU | 97.00% |
| `usr` | 22.24% |
| `sys` | 74.50% |
| 25G TX 峰值 | 约 20Gbps（25G 的 ~80%） |
| 阶段3 `>5ms` | 80.27% |

`sys` 占主线程约 74.5%，说明大部分时间花在内核 socket/TCP/拷贝上，而不是 Redis 命令逻辑（`cmdstat` 执行时间合计只占单核约 14.5%）。

UMS 是验证这个判断成本最低的方式：

- 不改 Redis 代码、不改压测业务代码；
- 只替换传输层，把“TCP/IP 栈 + 25G 网卡”换成“UB + 内核 URMA”；
- 可以直接和冻结基线做 A/B，量化“传输层到底值多少”。

### 1.2 UMS 是什么、作用是什么

UMS 是基于 SMC-R 思想实现的内核协议栈：

- **北向**：兼容标准 socket API（`socket/connect/accept/send/recv/epoll` 等）；
- **南向**：调用 UMDK-URMA（`ubcore_post_jetty_send_wr`，WRITE / WRITE_WITH_IMM）在 UB 上传输数据；
- **建链**：先用 TCP 完成握手，用 CLC 消息协商 UMS 能力、RMB 地址、Segment token、Jetty ID、Token 模式；
- **回退**：任一方不支持、版本不符或 Token 模式不一致，自动回退 TCP；
- **透明替换**：`ums_run` 设置 `LD_PRELOAD=libums-preload.so`，只劫持 `socket()`，把 `AF_INET/AF_INET6 + SOCK_STREAM` 映射成 `AF_SMC`。

本轮在 185/186 上已验证：

| 验证项 | 结果 |
|---|---|
| `ums.ko` | vermagic `6.6.12+`，两机加载成功 |
| `/proc/net/ums` | 存在，客户端连接 `UMS_ACTIVE / Fallback=False` |
| EID | 185 `...df00:0200` ↔ 186 `...df00:4200` |
| `send_lat 64B` | 中位 2.11us |
| `read_lat 4KB` | 中位 2.03us |
| `read_lat 200KB` | 中位 6.71us |
| `read_bw 200KB` | 47.9 GB/s（≈383Gbps，单 jetty） |

### 1.3 替换了 TCP 的哪些部分

| 层 | 是否替换 | 说明 |
|---|---|---|
| TCP/IP 分段/重组、ACK、重传、窗口、拥塞控制 | **替换** | UB WRITE / WRITE_WITH_IMM + UMS CDC credit |
| skb、软中断、25G 网卡驱动数据面 | **替换** | 内核 URMA + UB 设备 |
| socket 系统调用 | **保留** | `send/recv/epoll` 仍在，仍有用户态/内核态切换 |
| 用户↔内核拷贝 | **保留** | `send()` 拷到 sndbuf，`recv()` 从 RMB 拷回用户 |
| RESP 解析、Redis 命令执行 | **保留** | 应用层、事件循环、命令语义完全不变 |
| Value memcpy / 回复组装 | **保留** | Redis 仍把 200KB 值拷进回复缓冲；GET 的 6.78us 就是证据 |
| 主从复制路径 | **保留 TCP** | 备库 127.0.0.1:6380 故意不套 `ums_run` |
| TLS/加密 | **未涉及** | UMS Token 是访问控制，不是加密；本实验用 DISABLE |

**一句话**：UMS 替换的是“TCP/IP 协议栈 + 25G 网卡数据面”，不替换“socket API、两次拷贝、RESP、Redis 单线程命令执行和复制”。

### 1.4 部署与启动

1. 两机编译/安装 UMS（`umdk-ums` kmod + `umdk-ums-tools`），`modprobe ums ub_token_mode=2`（隔离压测用 DISABLE）；
2. 主库用 `ums_run redis-server ...` 启动，备库保持原始 `redis-server`（复制走 TCP 环回）；
3. 压测机用 `ums_run ./stress_test_opt8_urma ... --transport=ums` 启动；
4. 验证：`/proc/net/ums` 出现 `UMS_ACTIVE`、`Fallback=False`、SRC/DEST EID 和 JETTY_ID。

### 1.5 未改动的部分

- 40w key、80% 200KB + 20% 1KB、TTL=1s；
- 20 MGET（100 Key）+ 20 SET（200KB，2ms 间隔）+ 40 热 Key GET + 5 APPEND（5×200KB，100ms 间隔）；
- 阶段2 30s、阶段3 60s、5ms 业务阈值、100ms 读保护；
- key 选取规则、Redis 配置（`io-threads=1`、`io-threads-do-reads=no`）、主备拓扑、taskset。

## 3. 指标口径说明

- **阶段2**：预热完成后 30s，20 MGET + 20 SET，无热 Key/APPEND。
- **阶段3**：接下来 60s，增加 40 热 Key GET、5 APPEND、1 个热 Key 续期线程；阶段2 的读写线程继续运行。
- **业务 RTT**：客户端发出逻辑请求前到收到完整回复；MGET 是 100 Key 整体，SET/GET/APPEND 是单条命令。
- **`>5ms`**：逻辑请求 RTT 严格大于 5000us；失败请求单独计，不计入成功数。
- **CPU**：Redis 主线程单核 `%CPU`，`pidstat -t` 每 2s 采样，按 `test:phase:marker` 分桶；阶段3 稳态剔除最后一个 24% 边界样本（基线 19 条，方案8 20 条）。
- **`usr/sys`**：同一 `pidstat` 主线程行的 `%usr/%system` 平均；基线汇总表记 22.24/74.29，本文用逐样本重算的 22.24/74.50。
- **每命令 core-us**：`CPU 核数 / 命令数每秒`；阶段3 用 14,618/s 与 11,857/s。
- **RX/TX**：服务器 `/proc/net/dev` 每秒字节差分，阶段峰值；报告只统计物理网卡，不含 `lo`；`lo` 的复制流量用 `sar` 单独观察。
- **`cmdstat`**：INFO commandstats 的累计 `Δusec/Δcalls`；GET 的 6.78us 是 Value 拷贝仍在的直接证据。
- **UMS 门禁**：只统计客户端 `20.20.21.186` 的连接；`127.0.0.1` 是主→备复制，回退 TCP 是设计预期。

## 4. 怎么读这组对比

1. **传输替换确实生效，而且不是噪声**：阶段3 吞吐 +23.3%（> ±2.5%）、慢命令 -35.6%（> ±9%）、`>5ms` -38.31pp（> ±0.62pp）、25G TX -99.99%。
2. **平均时延和 5ms 比例都改善**：四类 avg RTT -8.7%~-25.5%，说明 UMS 把“中等排队”压到了 5ms 以下。
3. **CPU 没有变空闲，但每命令更便宜**：闭环压测把 CPU 重新打满；同负载估算 97%→约 80%，真实收益是“同样的 CPU 多干 23% 的活”。
4. **Value 拷贝仍在**：`cmdstat_get` 6.7→6.78us，几乎不变；MGET 26.81us、APPEND 59.51us 仍是主线程大头。UMS 只换了传输，没有换“Redis 怎么搬 Value”。
5. **剩余 `sys` 的来源**：
   - UMS 自身仍有两次用户/内核拷贝和内核 URMA 处理；
   - 主→备复制在 `lo` 上走 TCP，实测 619MB/s，CPU 完全没动；
   - 14,618 命令/s 的 socket 系统调用仍在。
6. **尾部出现了新问题**：GET/APPEND max 从 21/20ms 恶化到 63/64ms，四类命令 max 聚在 63~66ms，像 UMS 的共同停顿。第一假设是 **autocorking**：`ums_should_autocork()` 在“有未完成 Tx WR 且已准备发送量 ≤ min(snd_buf/2, autocorking_size)”时延后发送，等待首个 CDC 完成（`ums_tx.c` L159-L168）；当前 `autocorking=512KB`，200KB 回复会被 cork，等待 CDC 可能造成几十 ms 停顿。1MB snd_buf 已能装下 200KB，所以应先降 autocorking，而不是先加 buffer。`>5ms` 比例下降但 max 变差，说明分布从“普遍 5~20ms”变成“58% 很快 + 42% 很慢”。
7. **5ms 仍未达标**：41.96% 仍 >5ms，平均 RTT 仍有 4.4~6.2ms；UMS 是阶段性方案，不是终点。

## 6. 边界与注意事项

1. **单轮数据**：基线（20261022）与本轮（20261028）不是同一天；正式定版建议 3 轮取中位数，单轮内的 ±2.5% 吞吐 / ±0.62pp 5ms 不应下结论。
2. **闭环放大**：本轮命令数 +23.3%，UMS 省下的 CPU 被 MGET/GET 吸收，因此“CPU 仍 97%”不等于“没有收益”；要看每命令 core-us 和同负载估算。
3. **TTL=1、命中率 3.28%**：100×200KB 的 20MB 聚合仍未真正发生；本结论是“传输层/排队”的结论，不是“20MB 传输”的结论；TTL=0 场景需单独验证。
4. **UMS 不是零拷贝**：仍有 send/recv 两次用户/内核拷贝；GET 的 6.78us 就是 Value memcpy 未消除的直接证据。
5. **复制仍走 TCP**：`lo` 上 619MB/s（约 5Gbps）没有替换；生产跨机复制还会占独立链路，需单独规划。
6. **客户端 CPU 未采集**：本轮只采了服务端；40+ 客户端线程 + UMS 可能成为新瓶颈，下一轮必须补 186 的 CPU 和 p99。
7. **UMS Token 模式**：本轮用 `ub_token_mode=2`（DISABLE），仅适用于隔离压测；生产需两端统一 SECURE/LEGACY，并部署 `ums_agent`。
8. **尾部 63~66ms**：GET/APPEND max 恶化 3 倍，需排查 UMS 窗口/credit/重传定时器或 `net.ums.snd_buf/rcv_buf` 配置；不能只用 avg 下结论。
9. **最大 Key 2,048,000B**：与基线相同（两者都出现 2MB Key），不是本轮新增的混淆因素。
10. **`cmdstat` 是累计值**：MGET 26.81us 包含阶段2/3 的不同命中率，不能直接当阶段3 单条成本；趋势判断为主。

## 9. 轮1 → 轮2：autocorking 512KB → 16KB

### 9.1 为什么先调 autocorking

轮1 的尾部不是某一条命令变慢，而是四类命令的 max 共同聚在 **62.9~66.4ms**，同时 slowlog 出现 **GET 3.458ms**。这更像是发送侧的“攒包”停顿，而不是命令本身的执行时间。

UMS 发送侧有一个 `ums_should_autocork()`（`ums_tx.c` L159-L168）：

```c
corking_size = min(snd_buf_len / 2, ums->autocorking_size);
if (pending_tx_wr == 0 || prepared_sends > corking_size)
    return false;   // 不攒，立即发
return true;        // 有未完成 Tx WR，且已准备量没超过阈值 -> 先攒着
```

当“有未完成 Tx WR”且“已准备发送量 ≤ min(snd_buf/2, autocorking_size)”时，后续数据会先攒着，等第一个 CDC（连接数据控制消息）完成后再合并发出。轮1 的参数是：

```text
snd_buf = 1MB
rcv_buf = 1MB
autocorking_size = 512KB   # = snd_buf/2，已经是上限
```

200KB 的热 Key GET 回复低于 512KB 阈值，满足“可以攒”的条件；在 40 个热 Key 线程并发时，等待 CDC 完成可能累积到几十毫秒——这与四类 max 共同落在 63~66ms 的现象吻合。

**为什么不先加大 buffer**：1MB 的 `snd_buf` 本身已经能装下 200KB，单条消息并不存在“装不下”的问题；所以第一轮只改发送侧的聚合阈值 `autocorking_size`，不动 `snd_buf/rcv_buf`。

改动（两台都执行）：

```bash
sysctl -w net.ums.snd_buf=1048576
sysctl -w net.ums.rcv_buf=1048576
sysctl -w net.ums.autocorking_size=16384

sysctl net.ums.snd_buf net.ums.rcv_buf net.ums.autocorking_size
```

注意：`autocorking_size` 是建 socket 时读取的（`ums_mod.c` L900），**只对新连接生效**；必须让主控脚本重建 Redis、客户端重连，测到的才是新值。

### 9.3 结论

1. **autocorking 确实影响极端尾部**：四类 max 同步下降 6.5%~8.2%，slowlog 最大项从 3.458ms 回到 1.045ms，说明“等待 CDC 再发”是轮1 尾部的一部分。
2. **但它不是 42% >5ms 和 ~60ms 天花板的根因**：`>5ms` 41.96%→42.09%（+0.13pp，噪声内）、四类 avg RTT 变化 -2.2%~+0.6%、阶段3 吞吐 +0.06%，主体分布没有改变。
3. **代价在阶段2**：autocorking 变小后发送更频繁，阶段2 吞吐 -3.25%、SET max 从 5.4ms 回到 11.3ms、`sys` 从 56.55% 升到 61.13%。轮1 的 5.4ms 是“聚合红利”，轮2 把它还回去了。
4. **CPU 和 Value 拷贝没变**：phase3 `usr/sys` 26.29/70.52，主线程仍 97%；`cmdstat_get` 6.67us（轮1 6.78），Value memcpy 仍在；`cmdstat_mget` 26.66us、`cmdstat_append` 58.69us 也基本不变。
5. **怎么选**：
   - 尾部/max 优先：保留 `autocorking_size=16384`；
   - 阶段2 吞吐/小命令优先：回退 `512KB`；
   - 两者在 `>5ms` 上基本打平，16KB 不是明确的净收益。
6. **下一步不该继续调 buffer**：~60ms 共同尾部在 1MB 下仍然存在；应优先做“复制路径诊断（`REPLICAOF NO ONE`）+ 客户端 CPU/p50/p95/p99”，再进入 URMA 零拷贝，而不是继续加大 `snd_buf/rcv_buf`。
