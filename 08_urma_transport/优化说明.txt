方案4：URMA 数据传输（UMS 先行 + URMA 原生数据面）
============================================================

固定实验基线（与 20261022_195613 完全一致）
--------------------------------------------
MGET总聚合：100 Key
大Value：200KB（80%），小Value：1KB（20%），共 40w key
RTT超时判定：单条逻辑请求 RTT > 5ms
网络读保护超时：100ms
线程规模：MGET 20、SET 20、热Key GET 40、APPEND 5，THREAD_SCALE=1
阶段时长：阶段2 30秒、阶段3 60秒
预热：40w key，SET ... EX 1

方案定位
--------
本方案不改 Redis 命令语义、不改 MGET 聚合度、不改线程规模，只替换
客户端与服务端之间的传输路径。不引用方案1~3的任何代码。

为什么换传输层
--------------
冻结基线的主线程 CPU 为 97.00%，其中：
  usr = 22.24%，sys = 74.29%
而 INFO commandstats 的执行时间合计只占单核 14.5%。
也就是说，约 74% 的主线程时间花在内核 socket/TCP/拷贝上，而不是 Redis 命令逻辑。
因此本方案分两步验证：
  阶段A（UMS）：零应用改动，只把 TCP/IP 栈换成 UB，量化"传输层值多少"。
  阶段B（URMA）：命令环 + 描述符 + 单边 READ，进一步消除 RESP 解析和 Value 拷贝。

阶段A：UMS 透明替换（零应用代码）
----------------------------------
原理：
1. ums_run 设置 LD_PRELOAD=libums-preload.so，只劫持 socket()，
   把 AF_INET/SOCK_STREAM 改成 AF_SMC。
2. ums 内核模块先建 TCP 连接，用 CLC 消息协商 UMS 能力、RMB 地址、
   Segment token、Jetty ID、Token 模式。
3. 协商成功：send() 先拷贝到 sndbuf，再用内核 URMA WRITE/WRITE_WITH_IMM
   直接写进对端 RMB 环形缓冲；recv() 从 RMB 拷贝到用户缓冲。
4. 任一方不支持或 Token 模式不一致：静默回退 TCP。

能解决：
  - 去掉 TCP/IP 逐包处理、ACK、窗口、拥塞控制和 25G 驱动开销；
  - 数据改走 UB（本环境实测 200KB 单边 READ 6.71us、47.9GB/s）；
  - 零应用改动，快速验证 UB 的 EID/Token/模块/两机连通性。

不能解决：
  - Redis 单线程命令执行（14.5%）；
  - RESP 解析与回复组装；
  - Value memcpy（GET 200KB 6.7us、MGET 100 Key 31.8us 的主因）；
  - 20MB 大 MGET 的回复组装与单线程阻塞；
  - 仍有两次用户/内核拷贝（send 一次、recv 一次）。

阶段B：URMA 原生数据面
----------------------
MGET（与 baseline 同一条逻辑请求）：
  1. 客户端把 1 条命令 + 100 个 key 用 WRITE_IMM 写进服务端命令环；
  2. 服务端只做 dict 查找 + 过期判断，把 100 个描述符写回客户端回复环；
  3. 客户端对命中的 key 发单边 READ（读 slot_hdr + value）；
  4. 客户端校验 slot_hdr.version 与 expire_ms，完成整条逻辑请求。

SET/APPEND：
  客户端先把 value 单边 WRITE 到服务端授予的写槽（lease），
  再发提交命令；服务端不接收 200KB 载荷，只更新元数据与 Value 槽。

能解决：
  - Value 数据由网卡 DMA，服务端主线程不碰字节；
  - 去掉 RESP 解析/序列化；
  - 读取路径不再受单条连接串行约束；
  - 实测 UB 带宽 47.9GB/s，25G 以太网不再是瓶颈。

不能解决：
  - 字节总量不变（读回复仍需搬运，只是改走 UB）；
  - 写路径 APPEND 的扩容拷贝；
  - 复制路径（阶段B先保持 Redis 原生 TCP 复制）。

有效性门禁（不过就作废）
------------------------
1. UMS：/proc/net/ums 必须出现 UMS_ACTIVE 且 Fallback=False，
   并显示 SRC_EID/DEST_EID/JETTY_ID；Fallback=True 说明还是 TCP。
2. UMS：185 以太网 TX 应从约 20Gbps 降到接近 0；不降说明数据没走 UB。
3. UMS：INFO commandstats 的 MGET/GET/SET/APPEND usec_per_call
   应与基线一致（31.8/6.7/1.4/64.3），否则不是纯传输替换。
4. URMA：urma_admin show --all 必须 ACTIVE；客户端 --transport=urma
   能完成建链并输出 transport=urma。
5. 任何一轮失败数>0、丢包/错误>0，本轮不进入结论。

不能证明的部分
--------------
1. 字节量不变：本方案不减少读回复字节，只是换链路。
2. 20MB 聚合：当前 TTL=1s、命中率仅 2.71%，100x200KB 的 20MB 聚合
   从未真正发生。要证明"消除 20MB 长尾"，必须先补 TTL=0 常驻数据
   的基线重跑——这一点与其它方案相同，不能跳过。
3. 客户端 CPU：当前采集脚本只采服务端；阶段B需要补采 186 CPU，
   否则无法排除客户端成为新瓶颈。
