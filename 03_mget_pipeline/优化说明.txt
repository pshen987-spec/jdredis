方案B：MGET 拆成 10 批 x 10 条 GET Pipeline —— 实现说明
================================================================

0. 一页结论
------------
1) 只做方案B，方案A（对照组/A-B同源编译）已全部删除。
2) 基线保持不动、不再重跑：对照数据固定为 00_baseline/20261022_195613。
3) 方案B是在基线 stress_test_v2.cpp 上改“聚合方式 + 下发方式”的最小增量：
   场景参数、TTL、业务线程数(20读/20写/40热/5APPEND)、阶段时长、键选取规则、
   看护指标与基线逐字一致。
   **10批进入一个全局共享连接池(K=PIPE_POOL_CONNS, 默认20)，每连接深度
   D=PIPE_DEPTH(默认10)：读侧连接数固定为K，与基线20条读连接一致；
   在途批上限=K*D=200，在途key上限=2000。默认K=20,D=10可一次覆盖
   20个owner×10批；是否同时下发取决于队列，逻辑RTT可能含排队，
   但不再需要为了在途量把K放大到100/150/200。**
4) 改动量：客户端在基线源码上只替换读路径为“全局共享池 + FIFO 批次队列”；
   主控/采集脚本同步更新身份校验与连接数口径。
5) 跑前锁定的预期（不是结论，跑完由报告第[8.4]自动判定）：
   基线阶段2命中率仅0.85%、阶段2内存1.34GB->1.22GB，说明预热数据1秒即过期，
   那条“100键x200KB=20MB”的MGET回复几乎全是NIL，20MB聚合从未真正发生。
   因此本口径下方案B的预期代价是：命令数x100、共享池排队导致逻辑吞吐/逻辑RTT变差；
   可能有正收益的维度只剩“服务端单条命令的最长占用/单次回包尖峰是否下降”，
   客户端逻辑RTT不作为收益指标。

1. 实验目的与前提（必须先说清楚）
--------------------------------
方案A/B描述的问题现象是：一条 MGET 聚合100个200KB对象(20.48MB)，服务端要在一次
事件循环里完成100次查找+20MB序列化，主线程被单条长命令占住；客户端一个RTT要等完整20MB。
方案B的主张：把1个逻辑请求拆成100条独立GET(每10条一批)，服务端单条命令
从“100键+20MB”变成“单键200KB”；10批进入全局共享连接池，由K个lane线程
(K=PIPE_POOL_CONNS, 默认20)逐批取出执行，池内连接数固定，不随批次数膨胀。
注意：185是单主单备，没有分片；10批仍落在同一服务端，因此本轮能验证的是
“长命令拆短”的代价与尾延迟，不能验证“多分片分摊2MB/片”的收益（那需要真实Cluster）。

为什么改成全局共享池（而不是每worker 10条私有连接）：
  · 参考实现(redis++ std::async)是“每批一个任务 + 共享 pool.size=20”；
    本程序用同样的池模型：20个读worker把10批投入同一个FIFO队列，K个常驻lane
    线程各持1条连接，每个lane一次最多取 D=PIPE_DEPTH(默认10) 批执行。
  · 连接数：读侧固定K条(默认20)，与基线20条读连接一致，消除了“连接数x10”这个
    第二自变量；总连接约86条、进程约107线程(基线约87线程/86连接)，差异主要是
    20个owner线程。在途批上限=K*D=200，在途key上限=2000，与基线对齐。
  · 代价：默认 K=20,D=10 时，20个owner的200个批可以同时被20个lane各取10批，
    理论上一个请求的10批能在同一组内下发；只有在 D 调小或 K*D<200 时才会明显排队。
    如果仍要更深的在途，可加 D，而不是继续加 K/连接数。
  · 与参考实现的差别：参考的 pool=20 只面向“单请求demo”；本压测有20个并发owner，
    同一个20连接池会排队。这是本轮要量化的核心代价，不是实现缺陷。
  · 客户端参数不需要改：本方案用hiredis手写池，没有 redis++ 的 pool.size/wait_timeout；
    hiredis侧只用到超时（5ms判定/100ms读保护），与基线逐字一致；服务端redis.conf
    也不改（maxclients默认10000，20条读连接远低于上限；io-threads保持1/no）。

但基线冻结数据的口径是 WARM_TTL=1（预热也带 EX 1），预热完成后数据在1秒内全部过期：
  · 基线全程 keyspace_hits=643884 / misses=34132882 = 1.85%；
  · 阶段2命中率0.85%、阶段3命中率2.74%；
  · 阶段2采样内存 1.34GB -> 1.22GB（不是预期的约61GiB常驻）。
所以基线那条MGET的回复≈100个NIL，20MB聚合没有被触发。
本轮的定位因此是：在同一口径下量化“拆分本身的代价”，并把“收益验证需要数据常驻”
写成下一轮的前置条件；不把本轮的负结果误写成“方案B无效”。

2. 客户端改动清单（03_mget_pipeline/stress_test_opt3_pipeline.cpp）
------------------------------------------------------------------
沿用基线（未改，逐字一致）：
  WARM_KEYS=400000(80% 200KiB + 20% 1KiB)、PIPELINE=1000、WARM_TTL=1、WRITE_TTL=1、
  MGET_KEYS=100、MGET_THREADS=20、MGET_GAP_US=0、SET_THREADS=20、SET_GAP_US=2000、
  HOT_THREADS=40、APPEND_THREADS=5、APPEND_TIMES=5、STAGE2_SEC=30、STAGE3_SEC=60、
  RTT_TIMEOUT_US=5000、READ_TIMEOUT_MS=100、WARM_READ_TIMEOUT_MS=20000、THREAD_SCALE=1、
  热Key名 test:hot:activity:global、阶段标记 test:phase:marker=2/3/0。

改动的只有聚合方式、下发方式与记账：
  1) 1个逻辑请求 = 100条独立 GET，按 10条/批 拆成 10 批。10批进入同一个全局
     FIFO队列，由 K=PIPE_POOL_CONNS(默认20) 个常驻lane线程取出执行：
     每个lane独占1条连接，一次最多取 D=PIPE_DEPTH(默认10) 个批；
     全场读侧连接固定K条(默认20，基线20条)，在途批上限=K*D=200，
     在途key上限=K*D*10=2000，不再需要把K放大到100/150/200。
     每个读worker仍是1个owner线程，只负责生成100键、切批、入队、等10批完成、汇总；
     另加20个owner线程(基线20个读线程)。lane线程常驻复用，不随请求新建。
     --> 连接数/线程数与基线对齐；在途量由每连接深度提供，不再靠加连接。
  2) 发送：lane一次取到 n(<=D) 批后 append n*10 条GET，立刻 flush，然后同步读回
     n*10 条回复。hiredis 的 redisAppendCommand 只把命令堆进 c->obuf，真正 write
     发生在 redisGetReply 里，因此不显式 flush 的话批内会退化成逐条串行；
     这里直接调 redisBufferWrite(hiredis.h:330 / hiredis.c:1001) 把整组刷出去。
     池内K个lane可同时各刷 D*10 条，但同一逻辑请求的10批是否同时被取走取决于队列。
  3) 接收：每个lane按序读回本组 n*10 条（连接内FIFO），把结果写回各BatchTask；
     owner等10个BatchTask全部完成才结算1个逻辑请求。逻辑层与基线“1条MGET一次收完
     100个元素”同义，但t1额外包含批次排队、K条连接的回复解析与汇总开销。
     断连时lane自行 redisFree 并置空，下一组任务重连（与基线的重连语义一致）。
  4) 计数口径（两套，报告同时打印）：
       命令级：KeyGET = 发出的单键GET数；成功/失败/超时=命令级；
       逻辑请求级：MGET = 100条GET全部正常回复的请求数（与基线1条MGET同义）；
                  失败=未凑齐100条回复的请求数；超时=逻辑RTT>5ms的请求数。
     自检恒等式：KeyGET = 100 x (逻辑完成 + 逻辑失败)。
  5) RTT 由基线的4类(MGET/SET/GET/APPEND)扩为5类：MGET(逻辑100键)/KeyGET(单键GET)/
     SET/GET/APPEND；阶段2结束做快照，阶段3=全程-快照（与基线同算法）。
  6) 键选取与基线逐字一致：请求内位置 pos%5==0 取 test:data:small:<idx>，否则
     test:data:normal:<idx>，idx=均匀随机(0,399999)。这个规则本身会让32%的读永久落空，
     但基线就是这么测的，为保持对照不改。
  7) 错误回复(-OOM/-MOVED等)单独计数（基线把它算成功）；只增加一个计数器，不改变
     基线“成功/失败”的定义，因此不影响与基线已有字段的对照。
  8) append_worker 的既有空指针修复：handle_reply 在断连时会 redisFree 并置空 c，
     基线内层 APPEND 循环继续用 c 会段错误；现在销毁后立即 break 回外层重连。
     只在故障路径生效，正常轮的数字不受影响。

3. hiredis 与 Redis 服务端：都不改
----------------------------------
  · hiredis-v1.2.0 保持原样。用到的是公开接口 redisAppendCommand / redisGetReply /
    redisBufferWrite / redisSetTimeout，没有改库。
  · Redis 服务端零改动：命令从 MGET 换成 GET，不涉及配置项、模块、lazyfree、IO线程、
    分片或容器化；本轮也不验证跨Slot分散（单主单备，非Cluster）。
  · 集群落地注意：参考代码的 pipeline(首key) 只对“同Slot的10个key”成立；
    真正跨Slot要先按Slot分组、每组一条Pipeline再并发，否则会MOVED。
    本环境是单实例，不涉及Slot；不要把本轮结果当成Cluster验证。

4. 与冻结基线的对照可行性（哪些能比、哪些不能比）
-------------------------------------------------
能逐项对照（同口径）：
  逻辑请求吞吐（基线 MGET/秒 <-> 方案B 逻辑请求/秒；都除以30/60秒）
  逻辑请求RTT avg/max（基线 MGET <-> 方案B MGET列）
  服务端单逻辑请求成本（基线 cmdstat_mget usec/call <-> 方案B cmdstat_get usec/call x100）
  CPU 最高/平均、网卡 RX/TX 峰值、命中率、内存起止、主从offset差、网卡丢包增量
  逻辑请求 RTT>5ms 数（与基线 MGET 超时同义；本轮“命令级超时”按单键GET计，不与基线直接比）
  注：阶段3的 cmdstat_get 混入40个热Key GET线程，服务端成本判定统一用阶段2。

不能对照/需注明：
  · 基线没有 KeyGET 和逻辑请求级计数（那是旧实现，1条MGET）；
  · 基线没有“按命令类型拆分的 RTT>5ms”，只有阶段2/全程总数；
  · 基线 usec/call 与客户端计数来自同一批3秒采样但窗口不完全重合（约27s/55s），
    报告中已注明；方案B用完全相同的算法取数，属于同偏差对照。
  · 连接数已对齐基线20条，但“批次排队”是新增变量：同一逻辑请求的10批不再同时下发，
    逻辑RTT包含排队等待；K=20且20个owner时，排队是主要成本，不能把RTT变化全部归因于
    “命令拆短”。K可在编译期用 -DPIPE_POOL_CONNS 调整。
  · 共享池把“在途批次数”限制为K(默认20)：服务端同时最多收到 K×10 个key的GET；
    基线是20条MGET x 100键 = 2000个key在途。因此吞吐/RTT差异同时包含“命令拆短”和
    “在途量下降”两个因素；若要只比命令形态，需要K=200(在途2000键，但读连接回到200条)。
  · 本压测不保存/校验value内容，只校验每批10条、总计100条回复；键值对应的功能等价性
    不在本轮验收范围（参考实现的map合并只用于demo）。
  · 本轮不能证明“20MB聚合被拆分后收益多少”，因为20MB在基线口径下没有发生；
    要验证收益必须让40w数据常驻（WARM_TTL=0/WRITE_TTL=0），那需要重跑基线——本轮明确不做。

5. 预登记判据与决策树（跑前锁定，报告中自动执行）
------------------------------------------------
三个比值（全部来自报告[8]）：
  成本比   = 方案B cmdstat_get usec/call x100 / 基线 cmdstat_mget usec/call   (>1 更贵)
  逻辑吞吐比 = 方案B 逻辑请求/秒 / 基线 MGET/秒                                (<1 更慢)
  尾延迟比 = 方案B 逻辑RTT max / 基线 MGET max                                 (<1 削峰)

判定树：
  A) 成本上升 + 尾延迟未降  -> 本口径拆分无净收益；原因是MGET回复几乎全NIL、20MB未发生。
     结论只能写成“无数据时拆分只会放大命令数”，不得外推为“有数据时也无收益”；
     下一步若要验证收益，必须先定数据常驻口径并补跑基线（不在本轮范围）。
  B) 成本上升 + 尾延迟下降  -> 用吞吐/CPU换尾延迟；若目标是消除单条MGET独占主线程/
     20MB回包尖峰，方向有效；若目标是吞吐，不合算。
  C) 成本未升 + 吞吐未降    -> 本口径拆分无副作用，但没有收益证据（20MB未出现）。
  D) 成本未升 + 吞吐下降    -> 先看[9]的 KeyGET/逻辑请求是否≈100（批次是否真按10条
     下发），再核对共享池K是否过小(默认20；K<20时排队更重)，以及owner线程是否
     被客户端CPU压满；不要先归因于拆分本身。

任意一轮要“可用于对照”，报告[9]必须全部 ok：
  KeyGET = 100 x 逻辑请求（逻辑失败=0 时严格成立；有失败请求时差额=失败请求里
  因断连未append的GET数，报告会按解释项打印，但失败本身已使该轮不可对账）；
  阶段2快照差值在[0, 2000+100x阶段2失败]；命令守恒；逻辑请求失败=0；错误回复=0。

8. 风险与已知限制
-----------------
1) 连接/线程数：读侧固定K=20条连接(与基线20条一致) + 20个owner + 20个lane线程
   （进程总线程约107、到6379的总连接约86；基线约87线程/86连接）。
   连接数不再是自变量；在途量由 K*D 决定，默认 K=20,D=10 =
   200批/2000key，与基线对齐。
   若把 D 调小或 K*D<200，同一请求的10批会排队，逻辑RTT上升；
   这是深度参数的风险，不是连接数风险。判定时优先看 cmdstat_get usec/call
   （与排队/在途量无关）和逻辑请求吞吐，
   并同时核对[1]CPU/[2]网卡是否已被客户端压满。
2) 池内收包：KeyGET的RTT从lane开始append本批第1条算起，包含同批前序回复的传输/解析
   时间，但不包含批次在队列里的等待；服务端单命令真实成本看 cmdstat_get usec/call 与 slowlog。
3) 本口径命中率<3%，逻辑请求RTT的绝对值不代表有数据时的表现；
   任何“20MB是否被削峰”的结论都不能从本轮直接得出。
4) 计时的起止：逻辑请求t0=入队前，t1=10个BatchTask全部完成；与基线MGET的t0/t1同义，
   但t1包含批次排队、10条连接上100条回复的本地解析与汇总时间（基线是一次解析100元素数组），
   所以逻辑RTT的绝对值含共享池排队与客户端开销。
5) 阶段语义与基线一致：阶段2的dump是30s时刻的快照，阶段2的读写线程会继续跑到90s结束；
   因此“阶段3=全程-阶段2快照”，跨阶段数字不可与“阶段2结束”直接相加。
6) 上传门禁：客户端标识/参数/实现方式/基线口径(TTL=1s)/拆分形状(10批x10GET)任一不符，
   采集脚本拒绝上传并返回21-26，避免把非本方案数据归档到 opt3_mget_pipeline。
