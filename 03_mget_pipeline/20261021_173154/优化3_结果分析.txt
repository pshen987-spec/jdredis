优化3：MGET 拆分 + Pipeline 结果分析
====================================

测试轮次
--------
优化3：20261021_173154
对照基线：20261021_160056（当前正式基线）
测试条件：MGET 总聚合 800 Key，RTT 超时阈值 100ms，THREAD_SCALE=1。
优化3实现：一次 800 Key 的逻辑请求拆成约 80 条 MGET(10 Key)，通过 Pipeline 发送。

一、数据完整性
--------------
1. 主控返回码为 0，压测正常结束。
2. acceptance_samples.csv 共 98 条采样：阶段0为55条、阶段2为14条、阶段3为29条，无空行。
3. 压测期间主从复制异常采样为0，结束时主从 offset 相同。
4. RX/TX 丢包及错误增量均为0。
5. CPU、网络、命令RTT、逻辑MGET统计、内存和复制状态均已采集。

二、必须区分的两种 MGET 指标
-----------------------------
1. 报告普通 RTT 行中的 MGET，是拆分后的单条 MGET(10 Key)子命令。
2. “MGET逻辑请求”是完整读取800 Key的业务请求，由约80条子命令共同完成。
3. 因此，不能把优化3的单条 MGET(10 Key) RTT直接与基线的 MGET(800 Key) RTT当作同口径结论。
4. 评估业务效果时，应以完整800 Key逻辑请求的完成量、总耗时和超过100ms次数为主；子命令RTT用于观察Redis单次占用是否缩短。

四、正向结果
------------
1. 单条Redis MGET由800 Key缩小到10 Key，单条子命令阶段3平均RTT为5956 us、最大37735 us，单条子命令没有超过100ms。这说明大命令被拆短后，单次占用Redis主线程的时间下降。
2. 其他命令获得了更多调度机会。阶段3完成量相对基线：SET增加29.3%，GET增加31.3%，APPEND增加4.0%。
3. SET、GET、APPEND阶段3平均RTT分别下降28.1%、23.8%和15.7%，说明对其他请求的公平性有所改善。
4. 阶段3平均TX下降13.7%，TX峰值下降15.4%。
5. 测试期间无丢包、无网卡错误、无复制链路中断，结束时主从完全同步。

五、负向结果和限制
------------------
1. 完整800 Key逻辑请求的阶段3吞吐从654.1次/秒降到319.2次/秒，下降51.2%。
2. 完整逻辑请求超过100ms的次数从6次增加到75次，超时比例约为基线的25.6倍。拆分后的单条子命令虽然更快，但80条子命令全部完成所需的总时间更长。
3. CPU平均值仅下降0.4%，Redis单核瓶颈没有解除。大量子命令还增加了解析、调度及结果合并开销。
4. 阶段3平均RX增加26.1%，最大主从offset差增加到3892792字节。最终同步正常，但测试过程中的复制积压波动比基线大。
5. SET和APPEND最大RTT分别上升44.4%和11.0%，尾部延迟并非所有指标都改善。
6. Redis命令计数不能直接代表业务吞吐。一次逻辑请求被拆成约80条命令后，命令OPS会显著增大，但完整业务请求数反而下降。
7. 本优化只处理MGET拆分，没有大Key保护；APPEND造成的大Value问题仍然存在。

六、如实结论
------------
优化3达到了“缩短单条大MGET、改善其他命令平均RTT和降低TX压力”的部分目标，但当前 MGET(10 Key)、Pipeline深度8 的参数没有改善完整800 Key业务请求，反而使其吞吐下降约51.2%，逻辑请求超过100ms的次数由6次增加到75次。

因此，本轮结果应判定为：部分有效，暂不通过最终验收。它证明了拆分MGET可以改善命令公平性，但拆分粒度过细，客户端与Redis需要处理过多子命令。后续是否继续，以及改为每批50或100 Key、调整Pipeline深度，应与同事确认后再决定。本报告只记录本轮实测结果，未修改代码或测试参数。
